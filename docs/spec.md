# Spec: Ants v1

## Problem Statement

I hand AI agents real work: grilling me on an idea until it is clear, writing it up as a Spec, cutting it into Tickets, implementing them, reviewing, pushing and opening the pull request. Today I drive each of those steps by hand, one `claude` session at a time. I'm the one copying context between them, and I'm there for every step. Nothing runs while I sleep. I can't see at a glance which job is waiting on me. And every repeatable way of getting a job done lives only in my head and in loose scripts.

I want to draw how a kind of job gets done once, as a Process, then start a Run with a prompt and walk away. Agents should do the steps they can. The Run should wait for me only where I said it must, or where an Agent is truly stuck, and it should come back with a pull request and a Report. All of this has to run on my own Claude subscription, on my own machine, and keep going overnight.

## Solution

Ants is a standalone, single-user service on the user's machine. It runs Processes drawn in BPMN on an embedded Operaton engine. Each Agent Task runs one Skill through the unmodified AI CLI (`claude -p`, or `codex exec`) on Ants' own subscription login, never API tokens. Ants has one web UI and no other: drawing Processes, administering Agents, Skills and Templates, starting and watching Runs and their Transcripts, answering Rounds, approving, reviewing and pushing, the Tickets page, settings, and the Notification list of everything waiting on the user.

Ants ships five default Processes, each turning a prompt into a pull request:

- **Ship with me**, **Ship by proxy** and **Ship as proposed** run scout → grilling loop → to-spec → the user approves the Spec → to-tickets → implement each Ticket → walkthrough → Review changes → Push → Open pull request → Update the Vault. They differ only in who answers the grilling Rounds: the user, an Agent, or the recommendations.
- **Ship overnight** is the same, unattended up to Review changes.
- **Ship small** runs scout → propose a solution → implement → Push → Open pull request → Update the Vault.

Review changes, pushes and Vault writes always wait for the user. The Spec is approved wherever a Process draws an approval. A sixth shipped Process, **Set up Vault**, creates a Vault. The default Processes are built only from building blocks a user can draw.

## User Stories

### Installing, starting and updating

1. As the user, I want to install Ants with one `curl … install.sh | bash`, so that I never install a JVM or a package by hand.
2. As the user, I want the installer to verify the download against published checksums, so that I know the tarball wasn't tampered with.
3. As the user, I want `ants start | stop | restart | status | logs | run | rollback | password` in my terminal, so that I control the service without the UI.
4. As the user, I want Ants to run as a launchd agent that survives closing the terminal, crashes and logging out and in, so that Runs keep going overnight.
5. As the user, I want a second `ants start` to tell me Ants is already running and where, so that two instances never fight over the database.
6. As the user, I want Ants to create `~/.ants` on first start with no wizard, so that the settings page and the pre-Run check tell me what's missing.
7. As the user, I want Ants to detect `claude`, `git`, `codex` and `gh` through my login shell, and to offer a **Detect** button, so that it finds the tools I already use.
8. As the user, I want to install the web UI as an app (a PWA) with its own window, a Dock icon and a badge showing the Notification list count, so that Ants feels like an app without a second program.
9. As the user, I want Ants on `127.0.0.1:7323` behind a single-user login, so that nothing else on my machine or network drives my Agents.
10. As the user, I want Ants to refuse a non-loopback bind while the password is still the default, so that I can't expose it by accident.
11. As the user, I want the nav to show when a newer version is available and to offer **Update**, so that I stay current without leaving the UI.
12. As the user, I want an update to take effect only at the next restart, with the previous version kept for `ants rollback`, so that an update never kills a running Run behind my back and a bad one is easy to undo.
13. As the user, I want a Docker image of Ants, configured from the environment, with one data volume and a required password, so that I can move Ants to a server later.

### Logging in and settings

14. As the user, I want Agents to run on Ants' own Claude config folder and login, not my work login, so that the employer's Team seat isn't spent and my own hooks and plugins don't leak into Tasks.
15. As the user, I want the settings page to show the login status and the exact terminal command to log in, so that Ants never handles my credentials.
16. As the user, I want Ants to strip `ANTHROPIC_API_KEY` from every Agent's environment and check that no API key is in use, so that I'm never billed per token.
17. As the user, I want to set the command prefix and the environment allow-list per CLI (for example running `claude` inside the nono sandbox), so that sandboxing stays my machine's concern.
18. As the user, I want to point Ants at Varde's `config.toml` to reuse its command and env, so that I set up sandboxing once.
19. As the user, I want named lists of Vaults and Source maps with a default each, paired into named Profiles (such as `work` and `private`) with a default Profile, so that every Process, and every Run on its start form, can pick its own and work and private repos and knowledge never mix.
20. As the user, I want to list extra Agent folders and Skill folders, such as Varde's, so that Tasks can use Agents and Skills I already have.
21. As the user, I want to set how many Agent Tasks run at once (default 3), so that I control the load on my subscription.
22. As the user, I want to see the latest 5-hour and 7-day usage next to the login, so that I know how close I am to the Usage limit.
23. As the user, I want settings kept in one hand-editable `settings.yaml`, so that I can fix or back them up outside the UI.
24. As the user, I want dark mode that follows the system and then remembers my choice, so that the UI is comfortable at night.

### Drawing Processes

## Implementation Decisions

### Platform (ADR 0001)

- One Kotlin process on Spring Boot 4 (Java 25, Gradle with Kotlin scripts), embedding Operaton through its Spring Boot starter, with the REST and webapp starters so Cockpit is there for debugging. Engine state is in file-backed H2 locally and Postgres on a server.
- The Task worker runs in-process. It fetches and locks external tasks through Operaton's Java `ExternalTaskService`; there is no REST between engine and worker. Lock, retries and incidents come from the engine.
- The web UI is rendered on the server with JTE, as normal forms. Vanilla JS appears only where a page needs it, and live updates use SSE. There is no SPA and no bundler. `camunda-bpmn-js` and CodeMirror 6 come from pnpm at build time, with Node used only by the build; their `dist/` goes into the static resources. Each page holds one SSE connection, `/live`, carrying the sidebar's count, Runs line, pause and update notices and toasts, and the page's own parts as named events, since a browser shares 6 connections per host across its tabs.
- One hand-written stylesheet, `ants.css`, styles every page after the `prototype/web-ui` and `prototype/answer-screen` branches; light and dark follow the theme setting. The sidebar's **Light mode** / **Dark mode** writes the theme setting; the page shows whichever mode it isn't in. An action that leaves its page, such as Push, says what happens next in a toast on the page it lands on. A toast on every page says when a Round arrives or a queued Agent Task takes a free slot. Under `prefers-reduced-motion` nothing shimmers, flashes, fades, blinks, pulses, slides or spins; clocks and counts still update.
- Every markdown field is a CodeMirror markdown editor (`@codemirror/lang-markdown`): the start form's Markdown fields, Send on the Transcript and in the drawer, the Continue instruction, the Approve and Review changes comments, the Answer page's answers, an Agent's standing instructions, SKILL.md and the Ticket editor. Its toolbar has Bold, Italic (⌘B, ⌘I), Heading, List, Numbered list, Code and Link, **Preview** in a big modal, and **⤢ Expand**, the same editor in the modal beside a live preview. The server renders both previews with the CommonMark renderer the Approve page and the Report use. The template marks the field's textarea `data-markdown`; the textarea stays in the form, hidden, and carries what is posted, so the form works without JS and `required` still stops an empty one, the editor saying why. A page without a markdown field loads no CodeMirror.
- A pasted image in the start form or a Send is stored in `~/.ants/images` and referenced from the text; at a launch or a Send it goes to claude as an image block and to codex as `-i`. Pasting an image (a copied one or a screenshot to the clipboard) into any markdown field uploads it (`POST /images`), stores it as `images/<sha256>.<ext>`, and puts `![image](/images/<sha256>.<ext>)` at the caret, so the text stays plain text and a Schedule's stored value keeps working; pasted text pastes as text. Only PNG, JPEG, GIF and WebP, read from the file's bytes, up to 3.75 MB (5 MB as base64, what the Claude API takes in an image block) are stored; anything else is refused with a message and nothing is stored. Every reference in a prompt, its JSON inputs included, so any Task whose inputs carry it, or in a Sent message, goes with the text: to claude as a base64 `image` block before the text block of the stream-json user message, to codex as `-i <file>` on `codex exec`, which also adds it to an `exec resume` turn. A reference to an image that isn't stored stays text alone. The Transcript shows a referenced image where the message shows its text, and the Run log keeps the reference.
- Ships as an unsigned (ad-hoc) jlink tarball for macOS arm64, installed by `install.sh` into versioned folders with a linked `ants` launcher, plus a multi-arch GHCR image. CI releases on a major or minor version bump. There is no jpackage installer, no `.deb` and no systemd unit. A release holds `ants-<version>-macos-arm64.tar.gz` (`bin/ants`, `lib/ants.jar`, and a jlinked `runtime/`), its `SHA256SUMS`, and `install.sh`; a major or minor bump is a version `x.y.0` with no release yet. install.sh puts each version in `ANTS_HOME/versions/<version>`, links the one in use as `ANTS_HOME/current` and links `~/.local/bin/ants` to its launcher, then runs `ants start`; a checksum mismatch installs nothing.
- `ants start` installs and starts the launchd agent; `ants stop` uninstalls it as well as stopping it, so Ants stays stopped after logging in again until the next `ants start`. `ants logs` shows the end of `ANTS_HOME/logs/ants.log`, which launchd writes, and `ants logs -f` follows it. The lock file holds Ants' pid, written first thing at start, and the URL it listens on, added once it listens; while a live Ants holds it, another refuses to start and says where the first runs.
- The update check runs at start and every six hours: it reads the newest release's `SHA256SUMS` (`ANTS_RELEASES`, GitHub's latest release by default) and Anthropic's model status table (`ANTS_MODELS`). **Update** runs the release's `install.sh --update`, which installs the newest release into `ANTS_HOME/versions/<version>`, links it as `ANTS_HOME/current` and keeps the running version as `ANTS_HOME/previous`, also when an earlier Update moved `current` past it before a restart; the nav then names the version install.sh installed. Settings shows the running version and the update check's latest answer, with **Check now** to check at once; a check that can't reach the release list, Check now's or a scheduled one, says so on the Updates card. `ants rollback` swaps `current` and `previous` and restarts a running Ants. Installed by install.sh, the launchd agent runs `ANTS_HOME/current/bin/ants`, so launchd's own relaunches run the version an update or rollback left there. It runs with the PATH `ants start` ran with, since launchd's own lacks Homebrew's, so a CLI or a command prefix such as `nono` is found by name.
- The Docker image carries claude, codex, git and gh, runs as a non-root user, and keeps everything, the CLIs' logins included, on its one volume `/data`. Postgres is set with `SPRING_DATASOURCE_URL`, `_USERNAME` and `_PASSWORD`; without them the engine is H2 on the volume.
- `ANTS_HOME` (default `~/.ants`) holds everything Ants owns: `settings.yaml`, the lock file, logs, `shipped/`, the user's `agents/`, `skills/` and `templates/`, `claude/` and `codex/` config folders, `answer-history/`, and `runs/<slug>-<run>/` (Report, Transcripts, kept `tickets/`, and the Run workspace while it lives). Nothing hard-codes `~/.varde`.
- Single-user login on every address. The password defaults to admin/admin, changed in settings or with `ants password`. A non-loopback bind is refused while the password is the default. Settings shows the address Ants listens on; it is set when Ants starts (`SERVER_ADDRESS`), not in `settings.yaml`. Settings' **Check login** asks `claude auth status` again and says Logged in (with its method) or Not logged in. Docker requires `ANTS_PASSWORD` or `ANTS_PASSWORD_FILE`, which override `settings.yaml`'s password (while one is set, the settings page says so in place of its password field, and `ants password` refuses), and its UI shows an available update without an **Update** button. Ants has its own login page; **Log out** in the sidebar ends the session and returns to it.
- The PWA has a manifest and an icon. Installed, it has no browser bar, so the sidebar shows back, forward and reload in that mode only (`display-mode: standalone`). The manifest and icon are served without login; every other page needs it. The badge carries the Notification list count where the browser supports it; on macOS the browser badges only with notification permission, which the Notification list page asks for on a click.

### Process model and deploy (the Checks)

- Allowed elements: one start event (none or timer) per Process and per sub-process; none end; intermediate timer; exclusive and parallel gateways; Agent, User and Built-in Tasks; an interrupting timer boundary on User Tasks only; embedded sub-process; call activity; multi-instance (parallel or sequential) on Agent Tasks, sub-processes and call activities; text annotation and group. Everything else is a Check error naming the element, DMN and error events included, as is a multi-instance completion condition.
- An Agent Task is an external Service Task, topic `agent`, carrying extension properties `ants.agent`, `ants.skill` and `ants.resume`, plus the Vault and Answer History toggles (`ants.vault`, `ants.answer-history`; with neither set, the Skill's opt-in applies) and an optional result-schema override (`ants.result-schema`). Agents and Skills are referenced by name, never by path.
- A Built-in Task is an external Service Task whose topic names it (`clone-repos`, `accept-recommendations`, `push`).
- **Create and use** on a new Skill also adds it to the Task's Agent's `skills` when that Agent is the user's own; otherwise the Checks report that the Agent doesn't list it.
- Ants writes `operaton:` only, and rewrites any `camunda:` on the way in.
- **Save and deploy** goes through Ants. It refuses while any Check fails:
  - unknown or ambiguous Agent, Skill or `ants-uses` names, and `ants-uses` cycles;
  - a Skill the Agent doesn't list;
  - a missing or invalid result schema (a `${task.output.field}` read from a Task that promises none);
  - a `${task.field}` reference naming a Task or field that doesn't exist (a loop's element variable, `loopCounter` and `nrOf*` exist only on or inside that multi-instance);
  - a refused element;
  - an exclusive gateway with more than one path out and no default path;
  - a timer without a time;
  - a required call-activity field left empty, or a call activity calling a Process that isn't deployed;
  - a call cycle, or a Task a caller reads being renamed or removed (Saving a called Process runs its callers' Checks);
  - a Review changes **Send back resumes** naming a multi-instance Task;
  - a Schedule with a required start-form field that has no stored value, or whose times aren't six cron fields (seconds first) that Ants can read.
  
  An empty declared input is a warning, so a Skill that serves two Processes (`implement`, `pr`) declares every input either fills. More complex JUEL fails at runtime as an incident.
- Results: every Task's Result is one process variable named after its BPMN id, a JSON map. At Run start Ants sets every Task-id variable to `null`, so forward references read `null`. A loop overwrites it, so the latest wins. A User Task's Result fields (Approve `approved`, `comment`; Review changes those plus `comments`; Answer a Round `answers`) are offered by the input pickers and the condition builder as `${task.field}`. The condition builder's field picker offers what the decision can read, each labelled by where it is from: the start form's fields, the Results of the Tasks before the decision and their run counts (`runs.<task>`), Ants' own Run variables (such as `clones`), and a multi-instance's item.
- Run variables Ants keeps: `runs` (each Task's run count in this Run, for caps such as `${runs.grill >= 10}`) `clones` (every repo cloned so far, `[{name, path, commit}]`) and `sourceMap` (the repos of the Run's Profile's Source map, `[{name, remote}]`, read at Run start; ADR 0008). A Run with repos picked on its start form also has `ants.scope`, those repos (ADR 0011, 0014); any Run started while Profiles are configured has `ants.profile`, its Profile's name (ADR 0012).
- Call activity: the called Process runs inside the caller's Run and Run workspace, with one Report, the top Process's work branch, and the top Run's Profile, Vault and Source map, and Notification entries named after the top Run. Its start-form fields are its inputs, written as one `operaton:in` each. Its Result is every Task Result in the called Process, keyed by Task id. It is bound `latest`. A called Task's Transcript and Notification key is `<call-id>.<task-id>` (the call's key carries its `-<n>` when it is a multi-instance). The pre-Run check covers the Processes a Process calls.
- Multi-instance: the collection is an array field of an upstream Result, written as an expression that yields a Java Collection; each instance reads `${item}` (or its named element variable). Ants collects the instance Results itself, retrying on optimistic-locking clashes, into a list in instance order; an empty collection gives `[]`. A Task gives a list of its Results; a sub-process or call activity gives a list of `{taskId: Result}`, which in a sub-process includes its call activities' and inner multi-instances' Results. An instance's key is `<task-id>-<n>`, 1-based in item order, with one `-<n>` per multi-instance it runs in, outermost first (`draft-2-1`).
- Templates are small `.bpmn` diagrams in `~/.ants/templates` (the user's) and `~/.ants/shipped/templates` (read-only). Dropping one inserts a collapsed embedded sub-process that keeps the Template's ids, suffixed `_2`, `_3`, … only on a clash (an underscore, since `-` reads as subtraction in JUEL), with internal references rewritten, including the Task an **Asker**, **Send back resumes** or **Walkthrough** names (ADR 0009). Nothing links back after the drop.
- Schedules are run by Ants, not Operaton. A Process's Schedule is set in the modeler, on its start event; the Process page shows it (words, cron, next Run with a countdown) with **Pause**, **Resume** and **Remove**, and its **Add a schedule** opens the modeler. On deploy Ants keeps the drawn timer start but stops Operaton creating its start-timer job (ADR 0004), and Ants' own cron loop starts Runs through the same path as **Start**, pre-Run check included. A missed time runs once. An overlapping time is always skipped and noted. A Run that can't start becomes a `[failed]` Notification entry, whose page has **Start now** and **Dismiss**. Times that pass while a Schedule is paused are dropped on Resume. **Remove** deploys the next version of the Process with the timer taken off its start event.
- Start-form field types: Text, Markdown, Repos. Each can be required and can have a stored value, used by Schedules and to prefill the start form. The variable name is derived from the label and can be changed. The default Processes ask for `prompt` (required), a work branch the user may leave for the scout to name, and optional `repos` (Repos). A Repos field offers the Source map's names in a multi-select and takes typed-in entries, separated by commas or spaces: git URLs, and `owner/name` for a new repo Ants creates on GitHub. Any Repos field filled in picks the Run's repos (see Picked repos). Above its own fields every start form has an optional **Name** for the Run, such as "Tiny todo app"; left empty, and for a Schedule's Runs, the Run is named after its Process and start time ("Ship small, 12 Oct 21:40"). The name shows wherever the Run does (the Runs list, Home, the Notification list and its entries, the Run page and its tab title, the drawer, the Transcript, a Ticket's page, the Report and the Run log's first line), with the Process beside it; the Run's id stays the engine's UUID, shown small on the Run page. The Run page renames a live or ended Run; its Run workspace folder and work branch keep the name they started with. The name is the Run variable `ants.name`. A Run's name is trimmed and cut to 200 characters; a blank Rename keeps the name. A typed-in Repos entry of the shape `owner/name` (one slash, no scheme, host or `.git`) is a new repo; an existing GitHub repo is given by its URL, and a local repo by its absolute path. A user's own Process with a Repos field has its repos picked when that field is filled in.
- The Processes list shows, per Process, whether it is shipped or the user's, its Profile's Vault and Source map, its Schedule, **Ready** or **Can't start** from the pre-Run check, and its live Runs. **New Process** asks for a name and a starting point (blank or a copy of a Process), and also takes a BPMN file to import.
- The pre-Run check trusts a `gh auth status` that says logged in for a minute; a refusal is asked again on every check.

### Agent launcher (the worker)

- **Fetching:** one global cap on live CLI processes (`settings.yaml`, default 3), across all Runs and CLIs. The worker fetches only free slots, oldest ready external task first. Every launch takes a slot: first run, Continue, Start fresh, resume after a Round, a Send back or the reset, and **Try now**. Subagents run inside their Task's slot.
- **Holds before launch:** a paused CLI gate (see Usage limit) and, for **Items are Tickets** instances, a Ticket whose `Blocked by` isn't yet `in-review` or `done`. With **Items are Tickets**, each item names its Ticket by path or number (`tickets/issues/01-hello.md` or `01`). A `ready-for-human` Ticket's instance is held until the user marks it done, then completes without a launch.
- **Agent files** are Claude Code's subagent format: `name`, `description`, `cli` (claude or codex, default claude), `skills` (the Skills a Task may pick; an Agent without `skills` lists none), `tools`, `model`, and the standing instructions as the body. The body goes to `--append-system-prompt`, `model` to `--model`, and `tools` to an explicit `--tools` / `--allowedTools` allow-list. A file without frontmatter is an Agent with defaults, named after the file. Codex gets a sandbox setting instead of tools: the agent file's `sandbox` (`read-only`, `workspace-write` or `danger-full-access`, default `workspace-write`) goes to `--sandbox`, and any other value is refused (by the form, Import, the pre-Run check and the launch), never passed on; `model` goes to `-m`, and the body to `-c developer_instructions=…`.
- **Agents as Subagents:** an Agent with `ants-subagent: true` (the **Offer as a Subagent** tick box, off by default) is passed to every claude launch through `--agents`, so it's available as a Subagent type. The Agent tool's **Limit…** (by Subagent type) narrows which ones a given Agent may start; Ants enforces it by denying every other built-in or offered type (`--disallowedTools Agent(<type>)`), since claude starts any Subagent type that isn't denied. `--agents` is passed only to a Task whose tools include the Agent tool. Only `cli: claude` Agents can be offered; ticking it on a codex Agent is a Check error. A Subagent runs inside its Task's process, so the Task's permission mode, working directory and `--add-dir`s still bound it.
- **The command** is the CLI's command prefix from settings with Ants' headless flags appended. The environment is the settings allow-list, which Ants may narrow but never widen; a Secret goes only to a Protected Command's process, never to an Agent's. Ants always strips `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CODEX_API_KEY` and `CLAUDE_CODE_RETRY_WATCHDOG`, and always sets `CLAUDE_CONFIG_DIR` (`CODEX_HOME` for codex), `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` (the `subagent-depth` setting raises the depth).
- **Flags for claude:** `-p`, `--output-format stream-json --verbose --include-partial-messages`, `--input-format stream-json --replay-user-messages`, `--json-schema`, `--session-id <uuid>` set up front (`--resume` later), `--permission-mode dontAsk`, `--setting-sources user,project`, `--settings` with `disableAllHooks`, `--strict-mcp-config`, `--mcp-config` with Ants' MCP server and the Task's bearer token, `mcp__ants__run` in `--allowedTools`, Read and Edit of Ants' `secrets.yaml` and `settings.yaml` in `--disallowedTools`, `--disable-slash-commands`, `--forward-subagent-text`, `--add-dir` for the Vault and for the Answer History (each when on) and for each used Skill's folder, and the Run workspace as working directory. `Skill` is never in the allow-list. Guard against `--bare` becoming the `-p` default, since it would never read the login.
- **Secrets and Protected Commands** (ADR 0015): Settings keeps Secrets (a label, a write-only value shown as `••••`, and one or more variable names matching `[A-Z_][A-Z0-9_]*`) and Protected Commands (a command prefix such as `yarn` or `mvn deploy`, and the Secrets it runs with, by label). The labels, names and Protected Commands are in `settings.yaml`; the values are in `secrets.yaml` in ANTS_HOME, mode 0600, and the page never sends one back (saved blank, a value stays). Every claude Agent Task gets one MCP tool, `run(command, folder)`, served by Ants at `/mcp` on localhost and refused without the token of a live Task. Ants splits the command into words and runs it with no shell, picked by the longest Protected Command prefix that starts it, in `folder` relative to the Run workspace (refused outside it, symlinks followed), on claude's environment allow-list plus each linked Secret under each of its names, killing the process tree after 10 minutes. The tool returns the exit code and the combined output with every Secret's value as `••••`. A command no Protected Command starts is refused, and the error tells the Agent to end stuck with it in `needs`; the user adds the row and presses **Continue the session**. The threat is an accident, not a hostile Agent: Agents run as Ants' OS user, which is the ceiling, and a credential-injecting proxy the upgrade path. codex Agents get no `run` tool yet.
- **Flags for codex:** `exec --json --skip-git-repo-check`, `--output-schema` with a strict-mode Result schema written to a file beside the Transcript (every key required, `output` and `needs` nullable, no `if`/`then`/`else`, since codex sends it in strict mode; Ants drops a null `output` or `needs` and judges the Result against the full envelope; ADR 0003), `--sandbox`, `-m` and `-c developer_instructions=…` from the Agent, `--add-dir` for the Run workspace from an instance's folder and for the Vault (when on), then `resume <session>` when resuming, and `-` so codex reads the prompt from stdin. codex names a new session itself (`thread.started`'s `thread_id`), which Ants keeps for resuming. The Result is the turn's last `agent_message`, JSON under `--output-schema`, judged when `turn.completed` arrives.
- **The prompt** has the same shape for every Skill:
  1. The hand-off line: `Follow the Skill in <path> for the workspace at <Run workspace>.`, plus `It uses the Skills <name> (<path>) …` for the flattened `ants-uses` closure, plus ` The Vault is … and the Source map is ….` when the Vault toggle is on and the Run's Profile has a Vault, plus `The Answer History is …` when that toggle is on.
  2. The Task's declared inputs as one JSON object.
  
  Start fresh appends the user's instruction under "From the user:".
- **Result contract** (from the result-contract ticket): Ants builds the schema from the envelope plus the Task's promised `output` (`result.schema.json` beside `SKILL.md`, the Task's override, or `{}`), and enforces the two cases with `if`/`then`/`else` on `outcome`, since the API refuses a top-level `oneOf` (ADR 0003):
  ```json
  { "outcome": "done",  "summary": "<one sentence>", "output": { ... } }
  { "outcome": "stuck", "summary": "<one sentence>", "needs": "<free text to the user>" }
  ```
  Ants reads the **last** `result` line's `structured_output` and validates it again. If it's invalid, Ants sends the error into the same live session once, and a second failure is `[failed]`; a `result` line with no `structured_output` is a failure, not an invalid Result. File references in `output` are strings the Skill's schema marks `"format": "path"`, relative to the Run workspace root; one that is absolute or leads out of it, symlinks followed, is rejected. `stuck` never reaches the diagram: only `done` completes the external task.
- **Waiting:** `stuck`, a failure and **Stop** each become an Operaton incident (`handleFailure`, retries 0), holding the tag and the reason. When the user acts, Ants stores the choice and instruction as a local variable and sets retries to 1, and the worker resumes (`--resume`) or starts fresh (a new session id).
- **Failures are Ants' own:** a crash, an invalid Result after one retry, a lost login (`authentication_failed` or any `apiKeySource` other than `none` in `system/init`), a missing Skill, or a failed resume.
- **Stepping in:** stdin stays open. **Send** writes a user message, which reaches the live session at the next tool boundary. **Stop** sends an `interrupt` control request, and the `error_during_execution` that follows becomes a `[stopped]` incident, not a failure. Ants closes stdin once it holds a valid Result and none of its messages is in flight (a message is in flight until claude replays it, which happens at the next tool boundary or in a turn of its own after a `result`; the last valid Result counts). After that, Send is refused. `codex exec` takes no message mid-run: it reads its prompt from stdin to the end before its turn starts. So for codex, Send interrupts the turn (SIGINT, as Ctrl-C does) and resumes the session with the message once the process has ended, and the page says so; **Stop** sends the same SIGINT, and the turn it ends is `[stopped]`. A message Sent after a valid Result but before the turn's process has ended gets a turn of its own, and the last valid Result counts.
- **Transcript:** the raw stream-json lines are appended to `<Run workspace>/tasks/<task-id>/transcript.jsonl` as they arrive. Ants writes a divider per launch and its own system lines. The page replays the file, then follows it over SSE. A Task shows its session's context, as Claude Code's status line does (ADR 0016): the latest main-thread call's input, read from the cache or written to it (`input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens` of the latest `assistant` message's `usage`), with its share of the model's window once a `result`'s `modelUsage` gives `contextWindow`, as in `62k tokens (6.2%)`. One session has one context, so a Task shows its latest launch's, never a sum of launches or Tasks; a Subagent's calls read a context of their own and are left out, as are the So far rewrites. Subagent spawns match tool name `Agent` or `Task`, are grouped by `agent_id` (falling back to `parent_tool_use_id`), and get their lifecycle from the `task_*` system events. **So far** is a haiku rewrite of new Transcript lines every couple of minutes, in a session of its own, switchable off in settings; it is written into the Transcript as an Ants line with its tokens, and `so-far` in settings is `false` or how often it is rewritten (default 2m). The checklist comes from the task-list tools (`TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate` in claude 2.1.295; there is no `TodoWrite`). A codex Transcript holds `codex exec --json`'s lines, plus a user line Ants writes for each prompt, since codex prints none: `agent_message` items are text (the Result when it is one), reasoning is thinking, commands, file changes, searches and MCP calls are tool lines, and since `codex exec` prints no context per call, a codex launch shows its session's tokens so far, its last `turn.completed` usage (input plus output).
- **Usage limit:** a `rate_limit_event` with `status: rejected` gives `resetsAt`. One without `resetsAt`, a 429 `result` with no event, or a Subagent's `subagent_retry` with `rate_limit` means 30 minutes. On any of these Ants kills the process. Codex's "Try again at …" text (an `error` or `turn.failed` message saying "usage limit": "3:45 PM" today, else "Oct 13th, 2026 3:45 PM") is parsed as local time, with a 30-minute fallback ("Try again later."). Ants calls `handleFailure` with retries left and `retryTimeout` set to the reset plus one minute; this is not an incident and not on the Notification list. One in-memory pause gate per CLI makes fetched Tasks for that CLI re-pause straight away without launching. After the reset Ants always resumes with "The usage limit has reset. Carry on where you stopped." **Try now** opens the gate and unlocks the held tasks. There is no early throttling.

### Built-in Tasks

- **Clone repos:** input `repos` (Source map names or git URLs) and an optional `branch`. Each repo is cloned into `<Run workspace>/repos/<name>/` with `git clone --reference <local> --dissociate <remote>` at the remote's default branch. The work branch is checked out if it exists on the remote, otherwise created. The work branch is the one Clone repos recorded on the Run's clones (git config `ants.workBranch`), else `branch` (the start form's value, else the scout's), else `ants/<slug>`, the slug of the Run workspace's folder (`ants/<run-id>` for a Run without one). A branch held by another live Run (one whose clones were put on it) gets a counter suffix, `-2`, `-3` …. Landing and Push always use the recorded work branch, never the branch a clone happens to be on. The push URL is set to a dead value. Already-cloned repos and an empty list do nothing. A repo given by git URL is named after its last path part and cloned without `--reference`, as is a Source map repo whose local checkout is missing. The Result is `[{name, path, commit}]` for the repos this Task cloned (so running it again gives `[]`), and the Run's `clones` variable is updated. In a Run with repos picked it clones exactly those, whatever `repos` names, first creating each new repo with `gh repo create <owner/name> --private --add-readme` on the user's gh login and cloning it from the URL `gh repo view` gives in gh's git protocol; a new repo is created only when a Clone repos Task gets there. A default work branch `ants/<slug>` that any of the Run's remotes already has, as when an earlier Run of the same name pushed it, counts as taken and gets the counter suffix too; a branch from the start form or the scout is checked out and built on.
- **Accept recommendations:** completes a Round with every `recommendation`, `source: recommended`, and names the asker it resumes.
- **Push:** waits on its own page, which shows each repo's remote, work branch (new on the remote or updating an existing branch), base and commits, with how many files it changes and its lines added and removed (+/−). **Push** runs one `git push --dry-run` across all repos, then fast-forwards the work branch only, never force and never to the base. The Result has one entry per repo: `{repo, remote, branch, base, isNew, commits, pushed, error, compareUrl}`. A failed dry run pushes nothing, and a clone that isn't on the work branch fails its dry run; a rejection is `[failed]`, naming which repos pushed and which didn't, with git's message, and the user can push by hand from the kept clone (to the remote's URL, since the push URL is dead) and Continue. Continue, offered only on a `[failed]` Push, completes Push with what the remotes now hold, so a repo still unpushed has `pushed: false`. `commits` are the work branch's commits since the base, `[{sha, subject}]`; `isNew` means the remote didn't have the work branch when it was cloned; `compareUrl` is the forge's compare page for an https or ssh remote (GitLab's `/-/compare/`, else `/compare/`), null for a local one. **Cancel the Run** keeps the Run workspace. There is no Skip.
- **Landing** (implicit, not drawn): every Agent Task in an instance of a parallel multi-instance works in `instances/<key>/`, named by its Task key (`implement-2`, `draft-2-1`, `build-2.draft`). That folder holds a `git worktree` of each clone on `<work-branch>--<key>`, branched from the work branch head at launch, with symlinks for every other top-level entry and `--add-dir` on the Run workspace. On `done`, Ants rebases onto the current work branch in every repo, fast-forwards the shared clones, and removes the worktree and branch. Before any shared clone moves, every one must be clean, on the work branch, and an ancestor of the rebased instance branch; if one isn't, the landing is `[failed]` at once, naming the repo, nothing moves, and the instance keeps its worktree. Each Agent Task lands when it is done, so a later Task in the same sub-process instance branches from a head that holds the earlier one's commits. An instance's hand-off line names its folder as the workspace; file references in its Result stay relative to the Run workspace root. It lands one instance at a time per Run, all repos or none. With **Items are Tickets**, the instance's Ticket goes `in-review` as the instance ends, after its last landing. A conflict aborts the rebase and resumes the instance's session to resolve it, retried after each fix; after two rounds it is `[failed]`. Each round tells the session which repos conflict and that the rebase was aborted; the Agent rebases onto the work branch in its worktree itself, resolves the conflicts and answers again, and Continue after `[failed]` gets two new rounds. A rebase that fails for any reason other than a conflict is `[failed]` at once, and the instance keeps its worktree. An instance whose `repos/` holds anything that isn't a clone of the Run, such as a repo its Agent made with no clone to work in, doesn't land: it is `[failed]` at once, naming it, and keeps its folder. A stopped instance keeps its worktree for Continue, and Start fresh discards it. Single Tasks and sequential multi-instances use the shared clones.

### User Tasks

- **Answer a Round:** the page reads only `output.questions` of the named asker. On complete, Ants resumes the asker's session with the answers to its latest Round, whoever gave them, so the asker has no answers input. Round shape (from the answer-screen prototype):
  ```json
  { "questions": [ { "id": "…", "title": "…", "ask": "…", "context": "…", "recommendation": "…", "why": "…" } ] }
  { "answers":   [ { "id": "…", "answer": "…", "source": "accepted" | "written" | "agent" | "recommended" } ] }
  ```
  Ants stamps `source`, never the Agent. Every question gets an answer. An empty Round ends the loop, through a gateway. The page handles a task removed by a timer boundary. An Answer a Round is a User Task with `ants.user-task` set to `answer-round`; a User Task without `ants.user-task` is an Approve. Every Round answerer (Answer a Round, an answer-round Agent Task, Accept recommendations) names the Agent Task whose questions it answers with `ants.asker`; an Agent Task with `ants.asker` is an answer-round Agent, and Ants stamps its answers `agent`, a question it leaves unanswered getting its recommendation, stamped `recommended`. The asker is resumed with the Round's `{answers}` JSON as its message. A Round's number is its asker's count in `runs`, whoever answered the earlier Rounds.
- **Approve:** fields Title, Show (a Run workspace path or `${…}`, rendered as markdown) and Send back resumes (a Task id). The Result is `{approved, comment}`, and Send back needs a comment. Title and Show are input parameters `title` and `show`, so `${…}` works in them and the Checks read them; Send back resumes is the extension property `ants.send-back`. Show names a file in the Run workspace, or else its text is rendered itself. Send back resumes the named Task's last session with the comment alone; a Task with no session yet starts fresh with the comment under "From the user:".
- **Review changes:** fields Walkthrough (a Task whose Story set it shows; without it, By repo only) and Send back resumes (one Agent Task, resumed if it has a session, else started). Tabs are Story and By repo. The Result is `{approved, comment, comments[]}`, each comment Varde's shape `{story, step, repo, file, side, from, to, type, body}` with `type` one of ISSUE, NOTE, SUGGESTION or COMMENT. Approve sets every `in-review` Ticket to `done`. It is a User Task with `ants.user-task` set to `review-changes`; Walkthrough is the extension property `ants.walkthrough`, and its Story set is always `walkthrough/stories.json`. By repo shows each clone's commits on the work branch since the remote's default branch, newest first, and their diff (`origin/<base>...HEAD`). A line comment's `file` is relative to the Run workspace root, as Story set paths are, and its lines are on the side the user picked (`old` for a removed line, else `new`). Send back needs a comment or at least one line comment. It resumes the named Task with the comment followed by one line per comment, `- TYPE file:from-to (side): body` (with `, <story> step <n>` before the colon for a comment on a story step), which also goes to the Run log. The Story set is checked when the walkthrough gives a `done` Result: a failure is sent into the same live session, as an invalid Result is. Two rounds means one fix request (Varde's `ATTEMPTS = 2`); a set still failing after it is `[failed]`, naming each step and fault. A Story set that is missing, isn't JSON, or breaks the format is `[failed]` at once, with no fix round. A range's `base` is the commit it starts from, given as Varde gives it (the merge-base). Ants diffs `base` to `head` and reads old Sites at `base`, new Sites and citations at `head`. A Story set step is STALE when its Site's lines at its range's head differ from the same lines in the clone's HEAD now; the step shows both. The Story tab's Remainder lists each changed file of the Story set's ranges, by its repo and path, with how many of its hunks no step's Site touches.
- **Notification list:** a query over open User Tasks and incidents, plus failed scheduled starts and `ready-for-human` Tickets. Ants keeps no table that could drift. Tags are derived by Ants: ✕ `[failed]`, ⚠ `[stuck]`, ■ `[stopped]`, ? `[questions]`, ✓ `[approve]`, ± `[review]`, ↑ `[push]` and `[ready-for-human]`. Push's failures are ✕ `[failed]` with Continue and Cancel the Run. A `ready-for-human` Ticket of a live Run leads to the Ticket page, whose **Mark done** sets it `done`. **Next up** jumps to a new entry from the same Run within a few seconds of acting.

### Runs, Run workspace and Report

- The Run workspace is `~/.ants/runs/<slug>-<run>/` (minus what's kept), where the slug is the Run's name as it started in lowercase letters, digits and hyphens, at most 40 characters, and `<run>` the Run's UUID, so two Runs of one name never share a folder. The Run keeps the folder's name as the Run variable `ants.folder`, which every part of Ants finds the workspace by; a Run started before Runs had names keeps `runs/<run>/`. It holds `repos/`, `instances/`, `tickets/`, `scout/`, `proposal/`, `walkthrough/`, `vault/` (staged Notes and their proposal, ADR 0007) and the Run log (`run-log.md`): the Run's name and Process, then every Round, `[stuck]` instruction and user message, appended as they happen.
- **Picked repos** (ADR 0011, 0014): the repos a Run's start form names in any Repos field are the Run's, kept as the Run variable `ants.scope` with each Source map name replaced by its remote. They change only which repos the Run clones: Clone repos clones exactly them (see Clone repos), and the scout gets them as its `repos` input and takes them as given. Everything else follows the Run's Profile as in any Run: the Run keeps `ants.profile`, `sourceMap` holds its Source map's repos, the scout is launched, each Task gets the Vault when its toggle is on and the Profile has one, and Update the Vault runs. The pre-Run check needs no Vault when repos are picked: a Profile without one gives its Tasks none, the scout writes its brief from the prompt alone and update-knowledge answers `written: true` with nothing written. It checks each repo with `git ls-remote` and each new repo's name with `gh repo view`, which must fail, besides `gh auth status`. The Process page checks the stored values: without a Vault, a Process with a Repos field shows **Can't start unless its Repos are picked** and keeps **Start** enabled, and Start checks what was posted. The Run page and the Report name the picked repos. A Run started before ADR 0014 with `ants.scope` and no `ants.profile` reads as one with the default Profile.
- **Profiles** (ADR 0012): `settings.yaml` keeps named Profiles, each a Vault and a Source map by name (`profiles: {work: {vault: work, source-map: work}}`), and `default-profile` (else the first); the settings page lists, adds, renames and removes them and picks the default. A Process may name its Profile in the modeler's Process properties, the extension property `ants.profile` on the process. When more than one Profile is configured the start form shows a **Profile** choice, prefilled with the Process's, else the default, and switching it reloads the form for that Profile, its Repos choices and pre-Run check included; a Schedule's Run uses the Process's. At start the Run keeps its Profile's name as `ants.profile`, and from then on its Profile's Vault and Source map are the only ones it uses: `sourceMap`, Clone repos' names, the `--add-dir` and the hand-off line, the Vault write gate (ADR 0007), and a called Process (which uses the top Run's), so **Set up Vault** creates the Vault of the Profile its Run picked. The pre-Run check reads the Profile's Vault and Source map, and a Profile no longer in the settings is its one reason. The Run page shows the Run's Profile. With no Profiles configured nothing shows and every Run uses the default Vault and Source map; with one, no choice shows and every Run uses it. Picking repos doesn't change the Run's Profile. A Process, imported from another Ants, that names a Profile this Ants doesn't have can't start until the Process or the settings change.
- Home's Start a Run lists every Process, and marks one whose pre-Run check fails **Can't start**. The Runs list shows Coming up, then Live Runs with what each is doing now (its waiting entries, else its running Agent Tasks' live lines, else its queued or paused Tasks), then Ended Runs. A cancelled Run's row offers **Dismiss** while it keeps its Run workspace, and an ended Run's row links its **Report**. A live line's verb names what the latest event does and to what ("Reading Header.tsx"); with no event to name, a verb rotates. Clocks count from the launch's start and change only in the page, never by the server inventing progress. A waiting time reads as `2d 1h`, `20h 10m` or `12m`.
- The Run page lists the Tasks the Run has reached, in order, a called Process's where its call is, each with its Agent and Skill, its state and its session's context (a multi-instance's largest); a Task that a Cancel or a timer boundary ended reads Cancelled, not Done. A row opens the Task: its Notification entry while it waits on the user, otherwise its Transcript. A Task whose Round waits on the user reads "Waiting on its Round", and its page links to the Round.
- When a Run ends, Ants writes the Report mechanically, before cleanup: the start form, each Task's summary, the Rounds with sources (non-user answers listed separately), the Tickets, the `review` summaries, the Push and pull request Results, tokens, and links to the Transcripts. Cleanup then deletes the Run workspace except `tickets/`, the Report and the Transcripts. A failed or cancelled Run keeps the whole workspace until dismissed, with **Dismiss** on the Run page of a cancelled Run. A live Run's page has **Cancel the Run**, which ends it as the Notification list's does, and while the Run workspace is on disk the page names it and each repo in it (the shared clones, then each instance's worktrees) by full path. Pauses aren't in the Report. The Report is `report.md` in the Run workspace, headed by the Run's name and its Process (and its picked repos, if any), written as markdown, shown inline on an ended Run's page and from a **Report** link there. Each Agent Task's line gives its last Result's outcome and summary, its tokens and a link to its Transcript; Built-in Tasks add their own sections, the `review` section lists each Task's latest `output.review`, and the Pull requests section each Task's latest `output.pullRequests`. A cancelled Run's Report is written when it is cancelled; Dismiss only cleans up.
- The Answer History lives under `~/.ants/answer-history/`, one shared by every Profile (work answers can inform a private Run), one markdown file per Round of the user's own answers (the whole question, the answer, the source, Process, Run, Task and date), kept forever. Ants appends one line per question to `INDEX.md` (the title linking to its anchor, a short context, the Process and the date) when the Round completes.

### Tickets

- Matt Pocock's local-markdown tracker in the Run workspace: `tickets/spec.md` is the Spec, and `tickets/issues/NN-<slug>.md` are its Tickets (What to build, checkbox Acceptance criteria, a `Blocked by:` line, a `Status:` line, `## Comments`). The files are the truth. Ants ships an `issue-tracker.md` telling Skills where the tracker lives, and writes it into each Run workspace at `docs/agents/issue-tracker.md`, where the Skills look for it.
- Statuses: `ready-for-agent` and `ready-for-human` (to-tickets or the user), `in-progress` and `needs-info` (the implementer), `in-review` (Ants, on landing), `done` (Ants, on Review changes Approve), `wontfix` (the user). The Spec closes when the Run ends, or becomes `wontfix` if the Run is cancelled: Ants writes its `Status:` line (`closed` or `wontfix`), and a Spec without one reads as open.
- Web edits refuse to save over a file changed since it was opened; a tick saves only over the version the page showed, like Save. A refused Save shows the new version above the user's text, and saving again overwrites it. Pages follow file changes over SSE.

### Catalogue: Agents, Skills, Templates

- Settings list Agent folders and Skill folders. `~/.ants/agents` and `~/.ants/skills` always come first, and `~/.ants/shipped/` is always loaded. A Skill is any folder holding a `SKILL.md`, at any depth. An Agent folder contributes only the `*.md` files directly inside it. Names must be unique across all folders, except that a shipped Agent or Skill wins its name and the hidden one is shown greyed out, so tests and users avoid the shipped names (`scout`, `implement`, `pr`, …). Shipped Processes are `shipped/processes/*.bpmn`, deployed through the Checks on every start, each as its own deployment, so a start deploys one again only when Ants ships a change (ADR 0007). A user's Save of a shipped Process deploys a new version under its key, and a later Ants that ships a changed file never deploys over it: once the latest version under a shipped key is the user's, the shipped change is skipped (story 128).
- `shipped/` is owned by Ants and replaced whole on start when any file differs.
- Skill frontmatter keys Ants reads: `name`, `description`, `metadata.ants-inputs` (space-separated input names), `metadata.ants-uses` (space-separated Skill names), `metadata.varde-vault: true` and `metadata.ants-answer-history: true`. A Task gets the Vault if its Skill or any used Skill opts in, and the Task's toggle has the final say (ADR 0002). A used Skill's result schema is ignored.
- The admin pages write only to the user's folders. They support create, edit, copy, rename and delete, with **Used by** (deployed Processes, and the Skills that use a Skill); a rename or delete warns, and Ants never rewrites a Process. Import takes one markdown file into the create form, dropping unknown Agent keys with a notice and refusing broken YAML, a Skill without name or description, and an Agent whose `cli` is unknown. Edits reach live Runs at the next launch; nothing is snapshotted. The Skill page shows **Run by** (the Agents whose `skills` list it, with a warning when none does) and the Result fields its schema gives later Tasks.
- The model list comes from Anthropic's public model status table, refreshed with the update check; it shows when it was last checked, and **Check now** reads the table at once. Aliases show what they resolve to, deprecated models warn, and a custom ID is tried once by the pre-Run check. For a codex Agent the form shows a **Sandbox** select (`read-only`, `workspace-write`, `danger-full-access`) in place of the tool tick boxes, and the model is free text.
- The Agent form offers Claude Code's tools in groups (Read the code, Change files, Run commands, Web, Helpers), each saying what it does; **Limit…** holds one rule per field. Claude Code's other tools sit in a collapsed list, each with why it is usually off for an Agent. A tool Ants doesn't list can be added by name, with a note for `mcp__` tools, which need an MCP server Ants doesn't configure.

- **Scout rules:** the scout always runs in a Process that has one. It reads the prompt, the Vault and the Source map JSON (its `sourceMap` input, `${sourceMap}`), and never code. Repos picked on the start form come as its `repos` input, `${repos}`, empty when none was picked: it takes them as given, adding, dropping and questioning none, answers with them unchanged and writes in the brief what needs doing in each (ADR 0014). Else it picks the repos the work changes: the Source map names (matched loosely) and git URLs the prompt names, else the Source map names the Vault ties the prompt's subject to. The repos it picks never include one outside the Source map, nor a new one. A named repo that matches no Source map name or more than one, or work the Vault ties to no repo or to several it can't choose between, is `stuck`, with the closest Source map names in `needs`, so the user answers with the repos (ADR 0013). The brief is `scout/brief.md`: the prompt as understood, each repo and the prompt's words or the Note that tie it, relevant Notes as `[[Name]]`, and what the Vault doesn't answer; with no Vault, from the prompt alone.

Its schema, `story-set.schema.json`, lives in the walkthrough Skill's folder, where the storyteller reads it and Ants checks against it. When the walkthrough is `done`, Ants runs Varde's four mechanical checks (file missing, range out of bounds, a changed Site touching no hunk, citation absent). A failure resumes the session naming the failing steps; after two rounds it is `[failed]`. An unparseable file is refused whole.

## Testing Decisions

- **One seam: the running Ants service.** Tests start Ants with a temporary `ANTS_HOME` and an in-memory or temporary H2. They drive it the way the user does, through its HTTP pages, form posts and SSE, and assert only on what the user can see: the Notification list, Run and Task state, Results, Ticket files, the Report, the Transcript, and refs on git remotes. Tests never reach into Operaton tables or worker internals.
- **The AI CLI is faked through an existing seam:** the per-CLI command prefix in settings, the same knob the user uses for nono. A small fake `claude` executable reads its flags and stdin and plays a scripted stream-json session: `system/init` (with `apiKeySource`), assistant text, tool calls, `rate_limit_event`, an `interrupt` response, and a final `result` with `structured_output`. The script is picked per Task by Skill name, so one test can play stuck → Continue → done, an invalid Result → retry, a rejection → pause → resume, or a lost login. The fake also records the argv and environment it was launched with, so tests check the flags and environment hygiene (`ANTHROPIC_API_KEY` stripped, `CLAUDE_CONFIG_DIR` set, `--disable-slash-commands`, the hand-off line, `ants-uses` paths) from the outside. This follows Varde's "never test who is running" principle (varde-editor ADR 0004).
- **Git is real:** remotes are local bare repos, and the Source map points at them. Clone repos, worktrees, landing, conflicts and Push (including a rejected fast-forward) are asserted on the bare repos' refs.
- **Browser behaviour is tested in a real browser:** Playwright drives headless Chromium against the running service, in tests tagged `browser`. Locally, a Chromium that can't launch skips with the nono Seatbelt rules and `--no-sandbox` it needs; in CI (`CI` set), it fails instead.
- **Time is injectable** at the one place Ants reads it (the Schedule loop and pause-gate deadlines), so missed times, overlaps and resets are tested without waiting.
- **What makes a good test:** a whole user-visible behaviour through the seam. Examples: "a stuck Agent Task appears on the Notification list, and Continue resumes the same session id", "Save and deploy refuses a terminate end event and names it", "Ship small with a fake implementer ends with one pushed branch and a Report". Each test runs a small drawn Process, or a shipped one, end to end. Tests don't mock Ants' own modules, and don't assert on how a module is built.
- **What is covered:** the Checks (every refused element, every reference rule), the result contract, the incident and Notification list lifecycle, Rounds and the answerers, Approve and Review changes loops, call activities and multi-instance Result collection, the Blocked-by hold, landing and conflicts, Push, Schedules, the usage-limit pause, the concurrency cap, the catalogue (folders, name clashes, `ants-uses` resolution and cycles), Ticket status moves, the Report and cleanup, plus the five default Processes and Set up Vault run end to end against fake Agents.
- **Not covered by automated tests:** the shipped Skills' prose quality (the real model), visual layout of pages, and the PWA install. These are judged by the user on real Runs.
- **Prior art:** none in this repo yet; this is the first code. `scripts/burn.sh` in `oyvij/varde-editor` (a fresh `claude -p` per issue in a clone) is the closest shape. The throwaway prototype branches (`prototype/answer-screen`, `prototype/web-ui`, `prototype/default-processes`) are references for pages and diagrams, not tests.

## Out of Scope

- A plugin system in Varde.
- **Varde integration:** starting Ants from Varde, handing it Varde's Vault, Source map and workspace folder, or a Varde TUI or hook controlling Ants. Ants only prepares for it, through configurable paths and Varde's formats.
- An Ants TUI: the web UI is the only UI.
- A shared server for a team.
- Phone push notifications: the Notification list is enough.
- Paying per API token.
- Importing outside Skills and Agents, adapting them to Ants with an Agent, or syncing them with their source. The result-schema override already makes an unmodified Skill answer in JSON.
- DMN (a Business rule task): v1 routes on exclusive gateways.
- Knowledge without a Vault: v1 requires one, through **Configure a Vault** and **Set up Vault**.
- MCP servers for Agents: Agents start with MCP off. An `mcp__` tool can still be ticked by name.
- Moving to a server beyond the Docker image (a Helm chart and the rest).
- Going public: Developer ID signing and notarizing, Intel Mac, a Linux desktop package.
- Starting a Run from a hand-written Spec: every v1 Run starts from a prompt.
- Reading forge issues (scout, to-tickets) or starting a Run from one: v1 takes them pasted into the prompt.
- `sweep-knowledge` and a Sweep the Vault Process.
- A **Run a command** Built-in Task: an Agent with Bash runs the tests and reports.
- A generic **Form** User Task: a Round asks, and Approve covers a yes or no.
- A repo's own Skills (`.claude/skills` in a clone) in a Task's session.
